## Загрузка данных и автоматическое восстановление

### Обязательный процесс

1. Проверить конфигурацию источника, доступ к БД, TLS-проверку, одиночный lock и план диапазонов/снимков. Токены не печатать.
2. Запрашивать ограниченные интервалы с учётом endpoint-specific лимитов и общего rate limiter. Повторы должны быть ограниченными, с jitter и учётом retry headers.
3. Безопасно сохранить исходный ответ и метаданные запроса: marketplace, источник, окно, страница/cursor, HTTP status, время, run ID. Удалить секреты и чувствительные поля.
4. Отдельно определить валидный непустой ответ, корректный пустой ответ, усечение, ошибку формата и ошибку API. Ошибка парсинга не равна нулю строк.
5. Нормализовать, сохранив исходные ID, тип операции, временную метку, исходный знак суммы, ключи и сведения о версии преобразования.
6. Upsert по устойчивому ключу источника. Повтор одного чанка не создаёт дубли.
7. Зафиксировать completion record только когда доказана полнота запрошенной единицы. Для пустого полного ответа отдельный статус SUCCESS_EMPTY.
8. Сверить raw → normalized → loaded counts, покрытие ожидаемых единиц, дубли, суммы и ошибки. Только после этого продвигать watermark и разрешать downstream публикацию.

### Единица полноты по источникам

| Источник | Единица контроля | Условие завершения |
|---|---|---|
| Каталог товаров | полный снимок + все страницы | end-of-pagination/cursor, учтённое количество; пустой каталог подтверждён отдельно |
| Продажи | день/период × запрос | доказан конец пагинации и проверены пропуски внутри окна |
| Заказы | день/диапазон × cursor/offset | все страницы пройдены; при ограничении сохранён resume cursor |
| Финансы | день × последовательность ID операции (например rrdid) | pagination exhausted и дневная сверка; cursor и состояние дня сохранены |
| Реклама | кампания × окно дат | отдельный статус каждого campaign-window; empty не спутан со skipped/error |
| Остатки | снимок × страницы/склады | собраны все части снимка; лимит страниц не интерпретируется как нулевой остаток |
| Платное хранение | день отчёта × страницы/детализация | завершён отчёт и сохранён корректный empty-ответ |
| Карточки/конкуренты | объект × момент наблюдения | полнота снимка известна; отсутствие объекта не считается отсутствием изменения |

Если API не даёт доказать полноту, покрытие остаётся unknown/partial. Максимальная дата события и HTTP 200 не доказывают, что интервал полный.

### Состояния загрузки, watermark и catch-up

Статусы: SUCCESS, SUCCESS_EMPTY, PARTIAL, RETRY_WAIT, AUTH_BLOCKED, FAILED. Для каждого фиксируются run ID, диапазон, длительность, endpoint/category, запросы/страницы, retries и ожидание rate limit, cursor, число строк по слоям, expected/covered units, reconciliation и безопасный итог.

Watermark — последняя непрерывно закрытая единица источника, а не MAX(event_date) и не время последнего запуска. Загрузка учитывает окно поздних исправлений. При 401/403 источник останавливается до исправления credential; повтор тем же токеном не крутится. При 429 соблюдается retry hint и не создаётся шторм запросов. Сетевой сбой возобновляется только с сохранённой контрольной точки.

Замер восстановления сравнивает начальный checkpoint с текущей границей отдельно по каждому источнику. Отчёт должен показать время, запросы, ожидания, retries, полноту, разрывы, дубли, сверку и результат повторного запуска. «Быстро» не считается успехом без полного покрытия и сверок.

**Текущий статус:** действующего WB-токена сейчас нет. Проверка автоматического catch-up до текущей границы и фактическая скорость API — НЕ ПРОВЕРЕНО/БЛОКИРУЕТСЯ до появления credential. Исторический одиночный замер скорости не заменяет end-to-end тест.

**Текущие ограничения, обнаруженные аудитом:** bulk продажи не доказывают полноту всех страниц; проход заказов ограничен страницами и не везде устойчиво возобновляется из отдельного запуска; полнота рекламы контролируется по campaign-window; shortcut по внешней freshness-проверке отключён до появления подтверждённого completion ledger. Runtime не пропускает продажи, заказы и рекламу по одной максимальной дате: до появления проверенного completion ledger эти catch-up этапы выполняются повторно и должны быть идемпотентны. Продажи пока запрашиваются одной bulk-выдачей без доказательства конца страницы/покрытия. Отдельные WB runners товаров и остатков используют временные интервалы пропуска, в том числе после warning; это не доказательство полноты и должно быть устранено перед подтверждением catch-up. WB HTTP-клиент отклоняет `WB_SSL_NO_VERIFY=1`; все runner-скрипты оставляют TLS-проверку включённой. Для недоверенной CA настраивается доверенная CA, а не отключается проверка. Фактический catch-up остаётся НЕ ПРОВЕРЕНО без действующего токена.

### Сохранённые наработки загрузки — не удалять при чистке

В коде уже есть отдельные стратегии, их нужно укреплять и проверять, а не заменять общим новым загрузчиком без сравнения:

- **Финансы:** `scripts/wb_finance_canonical_default_runner_v1.py` выбирает bulk для закрытой истории и live-tail для свежих дней (по умолчанию последние 3 календарных дня). `scripts/wb_finance_canonical_bulk_runner_v1.py` и `scripts/wb_finance_canonical_live_tail_runner_v1.py` имеют разные режимы завершения; `scripts/wb_finance_canonical_closed_period_runner_v1.py` отвечает за закрытые периоды. У live-tail предусмотрено тихое первичное presence-зондирование → проверка, открыт ли источник → ограниченный follow-up → provisional материализация → строгая usable-закрывающая проверка. Rate-limit или отложенный контур никогда не доказывают пустой день.
- **Закрытые финансовые дни:** текущая последовательность использует продолжение с максимального rrdid, если день уже материализован; replay дня для контроля; повторную проверку после полезного прироста; затем saturation close. Saturation допустима лишь при terminal/no-content, отсутствии нового rrdid и роста суммы/диапазона после полезной итерации; duplicate-only хвост сам по себе не добавляет денег. Сохранён и принцип multi-pass close: page cursor действует внутри прохода, строки повторных проходов дедуплицируются по rrdid, сломанный cursor/429/пустой continuation завершает попытку, но не день; повторный проход начинает день с начала. Исторический stable-mode использовал минимум 3 прохода и требовал два последовательных прохода без новых строк/роста; текущий canonical mode дополнительно использует saturation checks. Количество проходов, паузы, endpoint-лимиты и RPS из экспериментов не считать вечными нормативами — сверять с кодом/тестами и перепроверять перед изменением.
- **Реклама:** `scripts/wb_ads_canonical_runner_v1.py` имеет очередь срезов campaign × date window, сохранение состояния и прогресс по completed/pending/retry/error. Сохранять эту декомпозицию и resume; не возвращать внешний freshness shortcut: до появления проверенного completion ledger он может перескочить внутреннюю очередь. `429` должен остановить/охладить соответствующий контур, а не создавать шторм.
- **Общий ingestion:** `src/ingestion/source_registry.py` описывает источник, chunking, grain и loaders; `src/ingestion/runner.py` создаёт run/chunk, пишет аудит и считает coverage/row loss; connector fetch → raw store → normalizer → idempotent upsert → publish gate. Это полезный каркас, а не доказательство того, что каждый endpoint уже полон.
- Raw страницы, resume/cursor, дневные статусы финансов, очереди рекламы, SQL сверки и тесты загрузчиков — часть накопленной работы. Сохранять и улучшать их при следующих итерациях; не заменять локальные scripts и данные массовой очисткой.

Текущие retry delays, page caps, RPS, concurrency и признаки close в раннерах — наблюдаемая конфигурация/история конкретной стратегии. Перед её переносом проверить действующие официальные лимиты API и тесты; не копировать экспериментальное число как правило без новой валидации.
