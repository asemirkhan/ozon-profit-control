# Обязательный протокол Codex и агентов

**DOC-ID:** PC-AGENTS-001 · **STATUS:** CANONICAL / ACTIVE · **SCOPE:** порядок работы, маршрутизация, роли и критерии завершения · **OWNER:** владелец проекта · **UPDATED:** 2026-10-30

`PROJECT.md` — реестр действующих правил и точка входа. Этот файл задаёт только порядок работы агентов; методики бизнеса находятся в зарегистрированных профильных документах.

## Перед каждым заданием — обязательно

1. Прочитать `AGENTS.md`, затем `PROJECT.md` целиком.
2. По таблице маршрутизации в `PROJECT.md` открыть все документы, помеченные для типа задачи как обязательные. Не заменять их поискoм похожих файлов.
3. Проверить статус документов и незакрытые решения. Использовать только `CANONICAL / ACTIVE`. `DRAFT`, `HISTORICAL`, `RETIRED`, выгрузки и архивы не являются инструкциями.
4. Сверить рабочее дерево и HEAD. Сохранить все уже существующие изменения владельца.
5. Если обязательная процедура отсутствует, имеет `OPEN/BLOCKED` решение или конфликтует с другим активным источником — остановить зависимую работу, назвать точные документы и запросить решение. Не выбирать правило по дате, названию, числу версии или собственной оценке.

**Приоритет:** явное последнее указание владельца → этот протокол → реестр `PROJECT.md` → профильный `CANONICAL / ACTIVE` документ в его области → код (доказательство текущего поведения, не утверждённое бизнес-правило). Любой исторический или черновой материал ниже по приоритету и не применяется для реализации.

## Контракт итерации

Перед редактированием зафиксировать цель, тип задачи, обязательные документы, именованные файлы, входные данные, проверяемый критерий готовности и пути вне области. Делать одну связанную итерацию. Параллельным исполнителям назначать непересекающиеся области файлов; одного владельца интеграции назначать всегда.

При изменении метода или правила обновлять его единственный канонический документ в том же change set, что и код, проверки и контракт выхода. Найти по репозиторию старые имена, ссылки, формулы и правила. Снять прежнюю инструкцию с действия: удалить её после переноса полезного, либо пометить `RETIRED — DO NOT USE` с прямой ссылкой на замену. Не оставлять рядом два активных плана. История изменения — Git, не копия файла с новым суффиксом.

## Роли агентов

- **Координатор / интегратор:** владелец границ задачи, реестра, файлового распределения, решений и итогового change set. Единственный, кто объединяет результаты.
- **Доменный исполнитель:** реализует ровно одну задачу по зарегистрированному документу; у него есть allowlist путей и критерии готовности. Не переписывает бизнес-метод по своему усмотрению.
- **Аналитик данных:** независимо проверяет зерно, покрытие, пропуски, дубли, источники и сверку. По умолчанию read-only; отдаёт запросы/вычисления и ссылки на исходные доказательства.
- **«Хейтер» / adversarial reviewer:** отдельный свежий контекст, только чтение. Получает задачу, канонические правила, критерии, diff и исходные доказательства, но не длинное обоснование автора. Должен опровергать: дать конкретный контрпример, путь данных/расчёт, файл и проверку. Итог `PASS`, `FAIL` или `UNVERIFIED`; отсутствие доказательств означает `UNVERIFIED`, а не одобрение. Не придумывает альтернативный бизнес-совет.
- **Ревьюер безопасности/релиза:** проверяет секреты, TLS, доступы, миграции, публикацию и восстановление в изменённых областях; read-only, если отдельно не назначен исполнителем.

Не запускать все роли всегда. Для небольшой правки — координатор и исполнитель. Для загрузки — исполнитель плюс аналитик или ревьюер. Для экономики, сигналов и рекомендаций — исполнитель и независимый «хейтер», а для расчётов также аналитик данных. Координатор сводит выводы и разрешает расхождения только по данным и каноническим правилам.

## Последовательность подключения

1. Координатор читает обязательные инструкции, проверяет Git-состояние и составляет короткий контракт итерации: цель, активные правила, scope, входы, список разрешённых файлов, критерии PASS и независимые reviewer-задачи.
2. Исследование можно распараллелить только на независимые области (например, API и схему БД). Исследователи read-only и возвращают факты с точными ссылками; не редактируют общий документ и не принимают бизнес-решение.
3. Координатор устраняет конфликт доказательств и фиксирует недостающее решение как `OPEN/BLOCKED`. Пока оно блокирует метод, исполнитель не начинает зависимую реализацию.
4. Один исполнитель меняет только свою область и обновляет единственный профильный документ в том же change set. Если задач несколько, файловые allowlist не пересекаются.
5. После готовности исполнитель передаёт diff, критерии и первичные доказательства аналитику/тестирующему. «Хейтер» подключается в отдельном контексте после реализации; он не видит длинное самооправдание автора и не меняет код.
6. Исполнитель устраняет замечания. Повторная проверка проводится по тем же критериям независимым reviewer; нерешённое `FAIL/UNVERIFIED` оставляет выпуск открытым.
7. Координатор проверяет gates, registry, diff, секреты и scope staging; объединяет разрешённые изменения, создаёт один Git change set и отправляет только согласованный commit.

Параллельная работа полезна для независимого чтения/извлечения и отдельных модулей. Она вредна для последовательной логики, общего файла или нескольких конкурирующих реализаций одного правила: там работает один исполнитель и один интегратор. Модель выбирается по типу шага, а не по престижности: быстрая модель для структурированного чтения и механических правок с точными критериями; сильная — для методики, неопределённой причинности, финансового правила и adversarial review. Независимый контекст снижает самоподтверждение, но сам по себе не гарантирует правильность; доказательство — воспроизводимые данные, расчёты и прохождение gates.

## Модель, навыки и проверка

Модель выбирать под сложность и доступность: быстрая для ограниченного извлечения/механики, рабочая для обычной реализации, наиболее сильная для неясной причинности, архитектуры и «хейтера». Модель не является источником истины и не заменяет расчёты.

Skill — повторяемая процедура и набор инструментов, не бизнес-правило проекта. Использовать установленный skill только когда его триггер совпадает с задачей; не копировать его в документы проекта. Для презентации применять имеющийся навык презентаций; бизнес-содержимое брать из `ECONOMICS.md`/`ANALYSIS.md`. Не создавать проектный skill, пока повторяемый процесс не стабилизирован и его нельзя выполнить обычной инструкцией.

Числовые правила подтверждать кодом/SQL/фикстурой; причину — трассировкой до исходных записей; публикацию — проверкой release gate. Агентское согласие не считается доказательством. Выполнять проверки, требуемые `QUALITY_GATES.md`, и записывать фактический результат. Не заявлять о непроведённой проверке.

## Git, данные и безопасность

- `.env`, ключи, реальные выгрузки и дампы не читать в вывод, не копировать в отчёты и не коммитить. До staging проверить каждый путь и staged diff. Использовать только именованные пути; не делать `git reset`, `git clean` и массовый `git add`.
- Считать GitHub публичным, пока не подтверждено обратное. Проверку TLS не отключать; при проблеме исправлять доверенную CA-конфигурацию.
- Не удалять данные, схемы, пользовательские изменения или неизвестные файлы до классификации и способа восстановления. Подтверждённый кэш/выход удалять только после проверки воспроизводимости.
- Один change set должен содержать актуальный документ, реализацию и релевантные проверки. Перед закрытием сверить реестр, удалить дублирующие текущие инструкции, проверить ссылки и `git diff --check`; коммитить только согласованные пути и отправлять в подтверждённую ветку без переписывания общей истории.

## Что означает «готово»

Итерация закрыта, когда критерии из канонического документа пройдены, независимая проверка завершена, документы и фактический код синхронизированы, не осталось конфликтующих активных правил и новых временных файлов, а итоговый коммит создан. Если необходимый доступ отсутствует, закрыть только независимую подготовительную часть и явно оставить зависимую работу `BLOCKED` — не выдавать её за завершённую.
