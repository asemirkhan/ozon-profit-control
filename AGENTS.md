# Profit Control — единые правила проекта и журнал работ

Это единственный главный файл проекта для инструкций агентам, текущего статуса, плана, критериев готовности и журнала итераций. Перед новой задачей агент читает этот файл и только те исходники/документы, которые непосредственно относятся к задаче. Не создавать ещё один план, журнал или файл «общих инструкций» без явной необходимости и согласования с владельцем.

## 1. Цель и рабочие правила

Profit Control собирает и сверяет данные Wildberries, рассчитывает экономику магазина и показывает владельцу только проверенные выводы и действия. Главный критерий качества — воспроизводимый результат, подтверждённый данными, кодом и проверками.

- Работать итерациями с одним главным результатом. До изменения описать цель, входные данные, затрагиваемые файлы, критерии приёмки и риски.
- Сначала читать `git status`, HEAD и нужные участки проекта. Текущая рабочая копия содержит обширные незавершённые изменения владельца: не делать `reset`, `clean`, массового форматирования, переименований или широкого `git add`.
- Не удалять файл только потому, что он временный на вид. Сначала определить назначение, восстановимость и наличие нужных данных. Удалять только установленный мусор, по точным путям.
- После каждой завершённой итерации обновлять разделы «Текущий статус» и «Журнал итераций» этого файла. Код и документация должны соответствовать друг другу.
- Проверки запускать по критериям приёмки задачи. Не заявлять о выполненной проверке, если она не запускалась. Если проверка обнаружила дефект, не считать итерацию завершённой.
- Факты, расчёты, гипотезы и неизвестное явно различать. Максимальная дата в таблице не доказывает полноту временного ряда.

## 2. Данные и рекомендации

- Сохранять исходный знак суммы, тип операции, время, идентификатор и исходные поля до документированного преобразования.
- Каждая сумма должна иметь зерно, источник и способ сверки. Нельзя объединять продажи, возвраты, отмены, логистику и корректировки только по похожему названию.
- Причинное утверждение допустимо только при прослеживаемых исходных событиях, устойчивом сопоставлении периодов и сверяемом денежном вкладе. Корреляция или условная модель не доказывает причину.
- Потенциальный эффект и экономию нельзя показывать как прогноз, если это лишь сценарное предположение.
- Если причина неоднозначна, данные неполны или суммы не сверяются — блокировать рекомендацию и сообщать, какую проверку нужно провести.
- Клиентский совет должен включать подтверждённый факт, одну выполнимую меру, окно проверки и измеримый результат. Не заполнять пробелы правдоподобным текстом.

## 3. Агентная система: роли и порядок

Мультиагентность использовать выборочно. Для небольших локальных правок и последовательной задачи достаточно одного агента. Для независимого аудита источников, сложного анализа причин и проверки безопасности запускать несколько ролей параллельно. Практический предел по умолчанию — три одновременно: координатор, один исполнитель/исследователь, один независимый проверяющий. Больше ролей добавлять только если у каждой отдельный результат и контекст.

### Роли

1. **Координатор / интегратор — всегда один.** Определяет границы итерации, контекст и критерии приёмки; назначает владельца каждому набору файлов; принимает или отклоняет результат; разрешает конфликты; обновляет этот файл; отвечает за коммит. Не передаёт разным агентам один и тот же редактируемый файл.
2. **Специалист по источнику / исполнитель.** Для WB отвечает за API, ограничения частоты, пагинацию, контрольные точки, идемпотентность и покрытие интервалов. Для рекомендаций отвечает за зерно данных, происхождение полей, сверку денежных сумм и преобразования. Получает только относящиеся к задаче файлы и конкретные критерии.
3. **Аналитик качества данных.** Независимо проверяет свежесть, полноту, дубли, пропуски, сдвиг схемы, зерно и сверку результатов. По умолчанию не редактирует код; возвращает запросы/расчёты и ссылки на доказательства.
4. **«Хейтер» / adversarial reviewer — только чтение.** Не наследует длинные рассуждения исполнителя. Получает краткую постановку, критерии, diff и доказательства. Ищет контрпример, неподтверждённую причинность, утечку данных, неполный крайний случай, несоответствие критериям. Для каждого замечания указывает точное место, сценарий отказа и способ проверки. Может отклонить решение. Не обязан предлагать другую бизнес-рекомендацию; предлагает кодовое исправление только если оно локально и доказуемо.
5. **Ревьюер безопасности/релиза.** Проверяет только релевантные для релиза риски: секреты, TLS, права доступа, локальные данные, миграции, восстановление, состав staged-файлов и историю Git. Не повторяет полный аудит продукта.

Не запускать все роли на каждой задаче. Для обычной правки достаточно координатора и исполнителя; для изменения расчётов — исполнитель, аналитик данных и «хейтер»; для загрузчиков/релиза — исполнитель и ревьюер безопасности, а при независимом анализе — также «хейтер».

### Контракт задачи агенту

В каждом задании указать: (1) единственную цель; (2) разрешённые файлы и запретные файлы; (3) используемые данные и их чувствительность; (4) критерии завершения; (5) требуемые проверки; (6) формат результата — изменённые пути, доказательства, ограничения, незакрытые вопросы. Агент не расширяет задачу молча. Параллельные задания должны иметь независимые файловые области или быть только для чтения.

## 4. Модели и навыки

- Лёгкую/быструю доступную модель применять для ограниченного извлечения фактов, форматирования, простых механических изменений и повторяемых проверок.
- Модель среднего/сильного уровня — для обычной реализации, межфайловой интеграции и диагностик, где нужно сопоставлять несколько источников.
- Самую сильную доступную модель оставлять для неоднозначных причинных выводов, архитектурных решений, безопасности и независимого adversarial-review.
- Модель не заменяет проверку. Критерии и примеры отказа задавать до сравнения моделей. Фиксировать время, качество результата и объём исправлений, а не только скорость генерации.
- Навык подбирать по выполняемой работе, а не назначать каждому агенту набор навыков «на всякий случай»:
  - `data-analytics:analyze-data-quality` — полнота, свежесть, зерно, дубли, пропуски и конфликт источников.
  - `data-analytics:metric-diagnostics` — диагностика изменения метрики и проверка возможных драйверов.
  - `data-analytics:validate-data` — независимая проверка источников, расчётов, графиков и выводов.
  - `data-analytics:product-business-analysis` — выбор действий после подтверждения причин и измеримых компромиссов.
  - `skill-creator` — только после того, как один процесс несколько раз успешно повторён и правила стабилизировались.
- Skills помогают выполнить конкретный анализ; инструкции проекта находятся в этом файле, а не в копиях одних и тех же правил.

## 5. Git, секреты и безопасность

- `.env` и реальные ключи остаются локальными. В GitHub не добавлять API-токены, пароли, приватные ключи, реальные выгрузки WB, дампы базы и персональные/клиентские данные.
- Считать репозиторий публичным, пока это не проверено заново. Перед коммитом проверять точный список файлов, staged diff, отсутствие секретов/выгрузок и `git diff --check`.
- Собирать изменения только по именованным путям. Не коммитить весь worktree ради «чистого дерева».
- Проверка TLS должна быть включена по умолчанию. Для нестандартного сертификата использовать проверенный CA bundle; не отключать проверку для обхода ошибки.
- Коммит делать после выполнения критериев итерации, затем отправлять в подтверждённый `origin/main` без переписывания общей истории.
- После каждой итерации оставлять в рабочей копии только намеренные исходники/документы. Сгенерированные файлы либо воспроизводимы и игнорируются, либо удаляются после проверки восстановления. Git — единственная история проекта; локальные альтернативные копии и дублирующие планы не плодить.

### Пошаговый план и критерии завершения

**Этап A — контроль TLS и сбор из сохранённого состояния.** Сначала включить TLS-проверку по умолчанию и проверить штатный CA trust. Затем заменить max-date/wall-clock пропуски подтверждённым состоянием завершения на реальном зерне источника; сохранять курсор/offset; корректно учитывать успешный пустой ответ, лимит страниц, `401`, `429` и сетевую ошибку. Проверить идемпотентность и восстановление после прерывания на сохранённых данных. Завершён только когда нет ложного пропуска интервала, повтор не портит данные, проверки зелёные, а журнала достаточно для диагностики.

**Этап B — измеренный live catch-up WB.** После появления токена выполнить автоматический сбор от последней достоверной контрольной точки до целевой даты. Для каждого источника записать длительность, число запросов/повторов, ответы и задержки, строку/суммы до и после, покрытие дат/окон, дубли, незавершённые задания и сверки. Завершён только при подтверждённой полноте и повторном безопасном запуске; до этого текущую скорость не заявлять.

**Этап C — инвентаризация и уборка проекта.** Составить по существующим путям перечень: рабочий исходник, воспроизводимый ресурс, локальный/чувствительный набор данных, историческое доказательство, временный кэш/мусор. Ничего неоднозначного не удалять. Для каждого подтверждённого временного файла определить, можно ли его пересоздать. Удалять точечно, проверять сборку/ссылки, коммитить согласованный набор. Этап завершён, когда нет необъяснённых путей и нет локальных секретов/данных в индексе Git.

**Этап D — система рекомендаций.** Сначала описать зерно, источники и знаки денежных событий; затем свести каждую сумму ровно один раз; проверить покрытие и неизвестные классификации; разложить изменение на проверяемые факторы; собрать контрпримеры; только после этого строить действия и UI. Этап завершён, если каждая рекомендация содержит доказанную причину, сверяемый вклад, одно действие и проверку результата, а adversarial-review не находит неподкреплённых причин или обещаний.

**Этап E — эксплуатация.** Документировать резервное копирование/восстановление, токены, мониторинг, ротацию секретов и выпуск; провести целевые проверки безопасности и восстановления; сохранить только проектные исходники и Markdown в GitHub, кроме локальных секретов/данных.

**Критерий закрытия любой итерации:** заявленная цель достигнута; применимые проверки выполнены; факты записаны в этот файл; лишние созданные этой итерацией файлы удалены или игнорируются; только проверенные пути закоммичены и отправлены.
