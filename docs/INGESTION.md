# PC-ING-001 — Загрузка данных

**STATUS:** CANONICAL / ACTIVE · **SCOPE:** все внешние источники и восстановление · **OWNER:** интегратор данных · **UPDATED:** 2026-10-30

Это единственный действующий документ о процедуре получения данных. Конкретный запуск или эксперимент — доказательство только того запуска, не инструкция. Если правила API изменились, проверить официальную документацию WB/Ozon и зафиксировать проверенную дату/ответ в change set.

## Цель и границы

Получить запрошенные данные без пропусков и дублей, сохранить проверяемую связь с исходным ответом, возобновить прерванную работу и явно сообщить степень покрытия. Максимальная дата строки, HTTP 200 или пустой ответ сами по себе не означают завершённый интервал.

Источник истины по коду: `scripts/run_profit_control_canonical_runtime_v1.py`, `src/ingestion/source_registry.py`, `src/ingestion/runner.py`, `src/connectors/{wb,ozon}/`, `src/normalizers/{wb,ozon}/`, `src/loaders/`. Это описание фактического пути при обнаружении расхождений; нормативные требования ниже имеют приоритет.

## Обязательная последовательность

1. **Подготовка.** Проверить здоровую БД, схему, singleton lock, доступ к API и TLS verification. Не печатать токен. Сформировать план целевых диапазонов/снимков и пропускную способность.
2. **Получение.** Запрашивать ограниченные чанки согласно контракту источника; соблюдать лимиты API, retry headers и один согласованный rate limiter на категорию/ключ.
3. **Сохранение raw.** Записать тело/метаданные запроса до преобразования, включая источник, временной диапазон, номер страницы/курсор, HTTP-статус и время. Секреты из заголовков, URL и тела удалить до записи.
4. **Проверка формы.** Различить корректный набор строк, подтверждённый пустой результат, ошибку/неожиданный формат и усечение по лимиту. Не превращать ошибку декодирования в ноль строк.
5. **Нормализация.** Следовать `DATA_MODEL.md`: сохранять исходные ключи, временные метки, типы и знаки; считать и показывать отброшенные/неразбираемые строки.
6. **Upsert.** Идемпотентный ключ определён в контракте источника. Повторный запуск обновляет тот же факт, а не дублирует его.
7. **Completion ledger.** После полного ответа записать целевой интервал/срез как успешный с покрытием и cursor/end proof. Успешный пустой ответ записать отдельно как `success_empty`. Частичный/усечённый/ошибочный ответ не закрывает интервал.
8. **Сверка.** Сопоставить raw → normalized → loaded counts, дни/сущности, дубли, суммы и незакрытые задания. Только затем обновлять watermark/публикацию.

## Единица завершения по источникам

| Источник | Единица покрытия | Что доказывает завершение |
|---|---|---|
| products | полный снимок каталога | последняя страница API, стабильный cursor и количество обработанных карточек; пустой каталог — явный успешный снимок |
| sales | день продажи × запрос | источник вернул конец пагинации/подтверждённый полный ответ; запрошенный период проверен по дням; `MAX(sale_date)` не закрывает пропуски |
| orders | день заказа × offset/cursor | страница короче лимита либо явный end-cursor; сохранён следующий offset при усечении; дата не закрывается только по наличию одной строки |
| finance | календарный день × последовательность `rrdid` | строгая финансовая сверка дня, pagination exhausted и reconciliation gate из `finance_day_state`; сохранить resume cursor |
| ads | campaign × окно дат | отдельная строка состояния каждого campaign-window; `completed` только при подтверждённом ответе; `success_empty` отличается от skipped/error |
| stock | момент снимка × все страницы/склады | snapshot завершён по всем страницам и площадкам; ошибка/потолок страниц не считается пустым остатком |
| paid storage | report day × detail/page | report закрыт, включая корректный пустой отчёт; пустой ответ не запрашивать бесконечно |
| card/competitor observations | объект × дата наблюдения | snapshot по каждому объекту; отсутствие карточки маркируется отдельно от отсутствия изменения |

Если API не позволяет доказать конец диапазона, источник получает `coverage=unknown/partial`, а не статус полного сбора. Утверждённые WB API лимиты и конкретное окно запроса записывать в конфигурацию кода; не превращать разовый RPS-эксперимент в постоянный лимит без проверки.

## Состояния и повторы

- `SUCCESS`: полная единица источника, контроль пагинации пройден, audit записан.
- `SUCCESS_EMPTY`: полный ответ подтверждён, строк нет; не равен ошибке или «не запускали».
- `PARTIAL`: часть страниц/объектов/окон получена; cursor и незавершённая часть сохранены, watermark не двигается за неё.
- `RETRY_WAIT`: временная сеть/`429`; ждать заголовки провайдера и bounded exponential backoff с jitter; не создавать параллельный повтор того же чанка.
- `AUTH_BLOCKED`: `401/403`; остановить источник, не повторять запросы с тем же токеном, потребовать обновления credential.
- `FAILED`: постоянная ошибка схемы/формата/конфигурации; сохранить безопасную диагностику и не отмечать покрытие.

Повторять только идемпотентный чанк. Не ретраить бесконечно, не трактовать `429` как отсутствие данных, не сбрасывать курсор на начало без записи причины. Глобальную concurrency/rate limit настройку менять только после проверки endpoint policy и соседних источников.

## Автопланирование и watermark

План цикла выводится из последнего успешного completion record каждого источника и обязательного overlap/revision window. Watermark — последняя непрерывно закрытая единица, а не максимальная дата строки и не время последнего процесса. Для источников с исправлениями/поздним закрытием повторно проверять скользящее окно и сверять, что обновления идемпотентны.

До появления completion ledger runtime не должен пропускать загрузку только по `MAX(event_date)` или wall-clock log. Выпуск отмечает источник как `unknown/partial`, продолжает только разрешённые независимые этапы, но не называет общую загрузку полной.

## Наблюдаемость и замер восстановления

Для каждого запуска сохранять `run_id`, marketplace, schema, source, диапазон, начало/конец, duration, endpoint/category, requests, statuses, retry wait, pages, cursor, raw/normalized/loaded counts, covered/expected units, duplicates, сумма сверки и итоговый статус. Удалять токены и персональные значения.

Live catch-up сравнивает начальный checkpoint с конечной границей по каждому источнику. Отчёт показывает время, API-запросы, ожидания rate limit, retries, покрытие, пропуски, дубли, балансы сумм и publish gate. Успех только если покрытие полно, сверки пройдены и повторный безопасный запуск не меняет результат необъяснимо. При отсутствии токена допустим только локальный/исторический анализ; текущую скорость не оценивать.

## Текущие блокеры реализации

- Runtime freshness для продаж, заказов и рекламы использует максимальную дату, способную скрыть разрывы.
- Продажи используют одно-страничный bulk путь без достаточного доказательства полноты.
- Заказы ограничены страницами на один проход; resume должен переживать отдельные запуски.
- В advertising runner есть campaign-window state, но внешний freshness gate может обойти эту очередь.
- У нескольких WB entry points `WB_SSL_NO_VERIFY=1`; live запуск блокируется до включения TLS verification.
- Для данных в этой рабочей копии нет доступного действующего WB-токена; live-проверка остаётся `BLOCKED`.

## Критерии приёмки изменения загрузки

1. Тест/фикстура показывает успех по нескольким страницам, усечение, пустой успех, `401`, `429`, сетевой сбой и resume.
2. Непрерывность проверяется на зерне источника, а не `MAX(date)`.
3. Повтор чанка идемпотентен; курсор не теряется после остановки процесса.
4. TLS verification по умолчанию включён во всех штатных entry points.
5. Raw → normalized → loaded и coverage report объясняются и воспроизводятся.
6. До live-токена кодовый этап может быть закрыт локально; сам live catch-up не закрывать без реального замера и reconciliation.
