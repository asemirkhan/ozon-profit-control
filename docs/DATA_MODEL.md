# PC-DATA-001 — Контракты и происхождение данных

**STATUS:** CANONICAL / ACTIVE · **SCOPE:** сущности, зерно, ключи, поля и lineage · **OWNER:** владелец модели данных · **UPDATED:** 2026-10-30

## Обязательный контракт любого слоя

Для каждой таблицы или опубликованного поля должны быть определены: business grain; primary/upsert key; площадка и схема; source system; event time и ingestion time; единицы измерения/валюта; nullable/unknown semantics; lineage к исходным записям; политика удаления/коррекции. Если хотя бы одно обязательное свойство неизвестно, поле нельзя использовать для причинного вывода.

Не подменять `NULL`, отсутствующее поле, parse error, неизвестную сущность и успешный ноль одним значением. Хранить raw identifiers параллельно с каноническим ключом. Unmatched оставлять видимым, а не присоединять к первому подходящему товару.

## Слои и их назначение

1. **Raw:** неизменённый ответ и метаданные запроса для аудита/повторного разбора; секреты предварительно удаляются.
2. **Staging (`stg_*`):** типизированное представление одного источника и его бизнес-событий; сохраняет source ID, event date, ingestion timestamp, marketplace, исходные значения и знак.
3. **Canonical facts/dimensions (`fact_*`, `dim_*`):** согласованные сущности и события для анализа нескольких источников. Трансформации сохраняют ссылку на source facts и правило маппинга.
4. **Marts (`mart_*`):** детерминированные агрегаты с зерном/окном из `AGGREGATION.md`; отдельно сумма по товарам, store-level и unmatched.
5. **Published snapshot:** версия согласованных данных UI. Файлы с разными snapshot ID нельзя показывать как одну подтверждённую публикацию.

## Основные WB staging таблицы и время

| Таблица | Сущность | Временная ось | Примечание к контракту |
|---|---|---|---|
| `stg_wb_product` | карточка/товар | `raw_updated_at` + время загрузки | снимок справочника; upsert по marketplace/source product identity |
| `stg_wb_sale` | продажа или возврат | `sale_date` | сохранить исходный тип события и знак источника |
| `stg_wb_order` | заказ/отмена | `order_date` | заказ не равен фактической продаже/денежному событию |
| `stg_wb_finance` | строка финансового отчёта | `operation_date` | исходный ID/rrdid, тип операции, source amount и знак обязательны |
| `stg_wb_ads` | метрика кампании | `date` | зерно содержит campaign и те товарные/placement dimensions, что реально пришли |
| `stg_wb_stock` | снимок остатка | `snapshot_date` | зерно включает товар, склад и тип доступности |
| `stg_wb_paid_storage` | строка платного хранения | `report_date` | сохранять детализацию источника и ключ распределения, если он есть |
| `stg_wb_competitor_snapshot` | текущая найденная карточка конкурента | `captured_at` | не равен непрерывной истории |
| `stg_wb_product_card_snapshot` | текущая своя карточка | `captured_at` | не равен непрерывной истории |
| `fact_wb_competitor_observation` | конкурент × свой товар × поисковая фраза × дата | observation date | историческое наблюдение с момента фактического запуска сбора |
| `fact_wb_product_card_observation` | товар × дата наблюдения | observation date | историческое наблюдение; отсутствующие прошлые даты не восстанавливать |

Поля и ограничения ключей должны быть дополнены по реальной схеме DDL и loader; название таблицы не заменяет подтверждение её grain. Для Ozon те же принципы фиксируются отдельно в нормализаторах/стейджинге с площадкой в ключе.

## Идентичность товара и соединения

Канонический товар связывается через marketplace-specific source IDs (`nm_id`, offer/артикул, barcode) и явную bridge-таблицу. Ключи из разных marketplace не объединять только по похожему артикулу. Однозначный join должен быть уникальным в пределах утверждённого времени действия mapping.

Для каждого соединения измерять: число совпавших, unmatched, неоднозначных, потерянных и раздутых строк; сумму до/после. Не использовать техническую заглушку вроде `~` как реальный ключ товара. `NULL`/unknown/unmatched остаются отдельными состояниями.

## Денежный контракт

Каждая денежная запись содержит исходную source amount с исходным знаком, валюту, идентификатор строки/операции, дату, source type, площадку и путь нормализации. Нормализованный economic impact хранится отдельным полем/слоем вместе с версией таблицы знаков. `ABS()` до фиксации source sign и типа запрещён.

Если тип операции неизвестен, запись попадает в unknown/unmatched bucket и остаётся в общей сверке. Суммы должны раскладываться как `source total = attributed to products + store-level + unmatched`, с документированным допуском округления. Никакая сумма не должна одновременно учитываться в товаре и общем слое.

## Публикация и происхождение

Каждый dataset/cabinet field имеет `snapshot_id` (или эквивалентный hash), `generated_at`, период, freshness boundary и статус полноты. UI выводит поля из одного подтверждённого snapshot. Незавершённая сборка не заменяет последний успешный опубликованный снимок.

Текущие раздельные JSON/CSV и фактическая связь полей с исходниками должны быть сверены и переведены на единый publish ID — это текущий gap, а не уже выполненная гарантия.
