# Контроль качества и условия публикации

**DOC-ID:** PC-QUAL-001 · **STATUS:** CANONICAL / ACTIVE · **SCOPE:** приёмка данных, расчётов, рекомендаций и публикаций · **OWNER:** интегратор релиза · **UPDATED:** 2026-10-30

## Gates по порядку

1. **Безопасность входа:** секреты только в окружении, TLS verification включён, схема/магазин заданы безопасно, операция имеет авторизацию согласно `API.md`.
2. **Источник:** за каждый required source/window есть completion state, граница свежести, покрытие, pagination/cursor proof и безопасный resume. Ошибка/пропуск/неизвестная полнота не равны пустому результату.
3. **Модель и агрегация:** уникальность ключей, grains, row-count conservation, orphan/fanout, source-to-loaded reconciliation и денежная сверка проходят допустимые границы.
4. **Методика:** формулы/знаки/mapping имеют статус решения владельца; аналитический вывод не сильнее доказательств; бизнес-решения не опираются на estimates, synthetic или incomplete data без явной маркировки.
5. **Согласованность публикации:** все клиентские поля относятся к одному immutable `snapshot_id`, включают generated_at, период, completeness и версии правил; атомарное переключение не смешивает старую/новую сборку. До реализации этого механизма customer-facing publication — BLOCKED.
6. **Клиентский смысл:** неизвестное, устаревшее, blocked и suppressed отображаются отдельно от нуля/нормы; текст ссылается на проверяемое доказательство.
7. **Восстановимость:** известны последний хороший snapshot, rollback, backup/restore и безопасный повтор.

## Статусы результата

`PASS` — доказательства приложены и все обязательные критерии пройдены. `FAIL` — критерий нарушен. `UNVERIFIED` — проверка не выполнялась или доказательств нет. `BLOCKED` — отсутствует обязательный доступ/решение/источник. Только `PASS` разрешает соответствующий publish. Нельзя заменять отсутствие доказательства агентским одобрением.

## Минимальный evidence bundle итерации

Цель и scope; список изменённых файлов; версии источников/правил; команды проверок и их реальный exit code; sample counts и сверки без персональных данных/секретов; результаты adversarial review, включая контрпримеры; открытые ограничения; документный diff. Проверки запускать только относящиеся к изменённым слоям, плюс обязательные проверки релизного маршрута.

## Релизные режимы

Диагностическая сборка может обновить локальные промежуточные данные, но не должна подменять published output или изображаться полноценным выпуском. Production default fail-closed. Любой явный bypass требует тестового профиля/изолированного каталога и заметной маркировки `diagnostic`; он не пишет поверх последнего успешного снимка.

## Действующие блокеры

По текущему аудиту: live WB недоступен без токена; несколько WB entry points отключают TLS verification; часть runtime проверяет свежесть через `MAX(event_date)`; полнота пагинации/возобновления не доказана для всех источников; production runtime default использует `diagnostic_build`; публикация не атомарна; финансовая методика не утверждена; API изменения не аутентифицированы. До закрытия соответствующего blocker нельзя утверждать соответствующий gate `PASS`.

## Документация и чистота

Изменённое правило обновляется в единственном canonical документе. Перед закрытием выполнить `.venv/bin/python scripts/validate_project_docs.py`, проверить локальные ссылки, отсутствие новых временных/дублирующих инструкций и `git diff --check`. Проверка валидирует наличие документов из реестра, `DOC-ID`, metadata, регистрацию активных файлов и уникальность scope. Политика удаления/снятия документов описана в `PROJECT.md`.
