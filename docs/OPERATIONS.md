# Эксплуатация

**DOC-ID:** PC-OPS-001 · **STATUS:** CANONICAL / ACTIVE · **SCOPE:** запуск, секреты, мониторинг, восстановление и релиз · **OWNER:** оператор проекта · **UPDATED:** 2026-10-30

## Нормальный ежедневный цикл

Контейнер `profit_control_runtime` должен быть в состоянии `Up`. В журнале успешного выпуска последовательно появляются этапы `bootstrap`, `finance`, `wb_non_finance_sources`, `marts`, `analytics` и `runtime_phase=complete`.

После выпуска необходимо контролировать:

- последний день продаж, заказов, рекламы и остатков;
- последний день финансового отчета и подтвержденную финансовую границу;
- дату пересчета `mart_pnl_daily_by_product`;
- время `generatedAt` обоих клиентских файлов;
- количество рекомендаций и долю заблокированных решений;
- сверку `mart_money_layer_reconciliation`;
- количество собственных изображений и список пропусков;
- появление наблюдений текущего дня в двух исторических таблицах карточек.

## Временные ограничения Wildberries

Ответ об ограничении запросов не должен порождать множество дополнительных запросов. Рекламный шаг завершается и основной выпуск продолжается. Платное хранение работает отдельной фоновой задачей и повторяет незагруженный диапазон в следующих циклах.

## Повторный запуск

Загрузчики и исторические наблюдения рассчитаны на повторный запуск одного дня. Повтор не должен удваивать деньги или историю. Перед ручным повтором следует проверить, что предыдущий процесс действительно завершен и файл блокировки не принадлежит живому процессу.

## Проверки перед изменением и выпуском

Запускать только проверки, относящиеся к изменённым слоям, плюс gates из `QUALITY_GATES.md`; указанные ниже команды — пример текущих точечных проверок, не полный release gate.

Python (рекомендации/ads rate limit): `.venv/bin/python -m unittest tests.test_recommendation_engine_v2 tests.test_wb_ads_runtime_rate_limit_exit`.

Кабинет: из каталога `cabinet` выполнить `npx tsc --noEmit --incremental false`, затем проверить три основные страницы в браузере.

Полный расчет аналитики: `.venv/bin/python scripts/build_profit_control_analytics_canonical_runner_v1.py`.

## Восстановление

Если исходные таблицы свежие, а кабинет старый, повторно запускается только аналитический сборщик. Если итоговые таблицы старые, сначала пересчитываются витрины. Если источник старый, повторяется соответствующая загрузка, а не весь исторический диапазон.

Нельзя вручную исправлять опубликованные JSON и CSV: следующий цикл перезапишет их. Исправление вносится в загрузчик, нормализатор, расчет или движок и подтверждается повторным выпуском.

## Безопасность и инциденты

TLS certificate verification обязателен для всех штатных запросов. Не разрешать `WB_SSL_NO_VERIFY` как production fallback. Секрет хранить в локальном окружении/secret store, ротировать при раскрытии; в логах и артефактах токен не появляется. При `401/403` остановить источник и запросить новый credential; при `429` уважать retry hints и общий limiter. При подозрении на повреждение данных остановить публикацию, сохранить последний хороший snapshot и восстановить из проверенного backup. Backup без тестового restore не считается проверенным.

## Известные ограничения реализации

- Docker должен быть запущен операционной системой.
- Текущий повтор выполняется через заданный промежуток после завершения, а не в фиксированное ночное время.
- История карточек и конкурентов честно начинается с даты включения накопительных таблиц; прошлые значения не восстанавливаются выдуманно.
- Граница окончательных финансов может отставать от оперативных продаж.
- До закрытия неоднозначных услуг и расчетного хранения уверенность части денежных рекомендаций остается средней.

Дополнительно: live catch-up без действующего токена не проводился; runtime ещё не обеспечивает все требования `INGESTION.md`/`QUALITY_GATES.md`; текущее значение `diagnostic_build` не является разрешённым production выпуском.
