# Сигналы и жизненный цикл отклонений

**DOC-ID:** PC-SIG-001 · **STATUS:** CANONICAL / ACTIVE · **SCOPE:** детектирование, приоритет, состояние и снятие сигналов · **OWNER:** аналитик продукта · **UPDATED:** 2026-10-30

## Разделение сущностей

Сигнал описывает наблюдаемое отклонение/условие. Гипотеза описывает возможное объяснение. Рекомендация предлагает действие и существует только по отдельному контракту `RECOMMENDATIONS.md`. Не склеивать эти три сущности в один уверенный текст.

## Определение сигнала

Каждый сигнал содержит стабильный `signal_code`, объект и grain, формулу/порог и версию правила, период наблюдения, baseline, факт и единицу, дату первого и последнего подтверждения, входные snapshot IDs, severity/priority, состояние, ограничения и причину подавления. Числовой порог не вводится до утверждения владельцем и проверки на исторических/синтетических случаях с анализом ложных срабатываний.

## Переходы

`candidate → active → monitoring → resolved` либо `blocked / suppressed`. `blocked` означает недостаток/несогласованность данных, `suppressed` — дубликат/перекрытие или низший приоритет при сохранении следа; эти состояния не равны отсутствию проблемы. Новый запуск не должен создавать новый сигнал на каждый день: использовать устойчивый ключ правила + объекта + эпизода и зафиксированное условие повторного открытия.

## Процесс

1. Проверить gate данных, baseline и правило версии.
2. Вычислить candidate на определённом окне и записать доказательство.
3. Проверить устойчивость/повторяемость там, где правило требует нескольких периодов.
4. Сопоставить кандидатов по одному объекту, убрать дубли по явной таблице приоритетов.
5. Сохранить все причины блокировки и подавления, опубликовать только единый snapshot.
6. На следующем цикле разрешить сигнал только по условию `resolved`, не потому что источник перестал присылать строки.

## Готовность

Проверить граничные значения порога, отсутствие данных, неполный день, дубликаты, повторный запуск, reopen и конфликт сигналов. Сверить precision/false-positive на размеченной выборке до активации. Любые неподтверждённые пороги в текущем движке — implementation gap; сам факт кода не утверждает бизнес-валидность.
