# Profit Control — единая база знаний проекта

**Статус:** единственный источник проектных правил и актуальных знаний. **Обновлено:** 2026-10-30. **Владелец решений:** пользователь проекта.

Это единственная проектная база знаний. Все агенты читают её целиком перед работой. Файл `AGENTS.md` — только технический входной протокол для Codex; он не содержит второй копии проектных правил. Git — история изменений; отдельные версии, архивы инструкций, changelog и параллельные планы не создаются.

## 1. Назначение и продуктовые границы

Profit Control собирает данные магазинов на маркетплейсах, сохраняет происхождение фактов, сверяет продажи и деньги, вычисляет проверяемые показатели и показывает продавцу подтверждённые сигналы и безопасные действия. В проекте есть Wildberries и Ozon; основной текущий поток и актуальный сбор — WB. Система включает Python ingestion/normalization/loaders, PostgreSQL, SQL-витрины, аналитические сборщики и Next.js-кабинет.

Система не должна выдавать корреляцию за причину, оценку за факт, отсутствие данных за ноль, незакрытый источник за полный период или синтетический пример за результат магазина. Если данные, методика или связь не подтверждены — вывод ограничивается фактом либо блокируется.

## 2. Источник истины и принятие решений

Приоритет правил: последнее явное решение владельца → этот файл → код как описание фактического поведения → никакие старые локальные заметки/эксперименты не задают норму. Код не становится бизнес-правилом только оттого, что он исполняется.

У каждого важного правила в этой базе фиксируются: что делаем, почему, входы, выходы, исключения, доказательство/критерий готовности и статус решения. Используются статусы:
- **УТВЕРЖДЕНО** — владелец принял правило; реализация обязана ему соответствовать.
- **ОБЩИЙ КОНТРОЛЬ** — инженерное правило безопасности/качества проекта.
- **ОТКРЫТО** — бизнес-решение не принято; нельзя додумывать или выдавать за норму.
- **ТЕКУЩИЙ ДЕФЕКТ** — подтверждённое расхождение текущего кода с требованием.
- **НЕ ПРОВЕРЕНО** — нет достаточного доказательства.

При конфликте, отсутствии обязательной процедуры или решении со статусом ОТКРЫТО исполнитель останавливает только зависимую часть работы, указывает конкретный пробел и продолжает независимые задачи. Нельзя выбирать правило по дате, названию файла, уверенности модели или числу голосов агентов.

## 3. Карта проекта и поток данных

Основной путь: API площадки → сохранённый raw-ответ и audit → нормализованные факты → PostgreSQL → marts/сверки → аналитические сигналы → рекомендации → единый клиентский snapshot → кабинет/API.

Основные точки кода:
- Runtime: `scripts/run_profit_control_canonical_runtime_v1.py`.
- Общий ingestion: `src/ingestion/`, реестр источников и runner.
- Адаптеры WB/Ozon: `src/connectors/`; преобразование — `src/normalizers/`; загрузка — `src/loaders/`.
- DDL: `src/loaders/ddl.sql`; расчёт витрин — `src/marts/`.
- API: `src/api/main.py`.
- Движок рекомендаций: `src/services/recommendation_engine_v2.py`; сбор клиентских наборов выполняется scripts-раннерами.
- Кабинет: `cabinet/`; публичный сайт: `web/`.

Это ориентиры по коду, не гарантия полноты или корректности. При перемещении кода обновлять этот раздел в той же итерации.

Наблюдаемый runtime проходит bootstrap → загрузка required sources → marts → analytics/recommendation packs → cabinet. Ограничение одного необязательного источника не должно молча маркировать общий результат полным. Контейнеры подключают рабочий код и локальную БД; для воспроизводимого production нужна сборка из фиксированного commit/image.

Основные страницы текущего кабинета: `/economics` — магазин; `/products` — список и фильтры; `/products/{product_key}` — товар, доказательства, экономика и действия; `/internal/data-health` — диагностика. Python API в `src/api/main.py` обслуживает health, store summary/overview, actions, products, playbook, data-quality, rule-map, product-extremes, unmatched money и replenishment. Это карта текущего кода; контракт каждого endpoint перед изменением сверять с реализацией и схемой ответа.

Кабинет сейчас читает несколько JSON/CSV payloads, в том числе human pack и recommendations pack; их атомарная публикация под общим snapshot пока не доказана. Временная атомарная запись одного JSON не делает несколько файлов согласованными. Последний хороший набор должен оставаться доступным до прохождения publish gate. **ТЕКУЩИЙ ДЕФЕКТ:** production runtime имеет default `diagnostic_build`, который может обходить publish gate; этот режим нельзя считать production publish.

## 4. Загрузка данных и автоматическое восстановление

### 4.1 Обязательный процесс

1. Проверить конфигурацию источника, доступ к БД, TLS-проверку, одиночный lock и план диапазонов/снимков. Токены не печатать.
2. Запрашивать ограниченные интервалы с учётом endpoint-specific лимитов и общего rate limiter. Повторы должны быть ограниченными, с jitter и учётом retry headers.
3. Безопасно сохранить исходный ответ и метаданные запроса: marketplace, источник, окно, страница/cursor, HTTP status, время, run ID. Удалить секреты и чувствительные поля.
4. Отдельно определить валидный непустой ответ, корректный пустой ответ, усечение, ошибку формата и ошибку API. Ошибка парсинга не равна нулю строк.
5. Нормализовать, сохранив исходные ID, тип операции, временную метку, исходный знак суммы, ключи и сведения о версии преобразования.
6. Upsert по устойчивому ключу источника. Повтор одного чанка не создаёт дубли.
7. Зафиксировать completion record только когда доказана полнота запрошенной единицы. Для пустого полного ответа отдельный статус SUCCESS_EMPTY.
8. Сверить raw → normalized → loaded counts, покрытие ожидаемых единиц, дубли, суммы и ошибки. Только после этого продвигать watermark и разрешать downstream публикацию.

### 4.2 Единица полноты по источникам

| Источник | Единица контроля | Условие завершения |
|---|---|---|
| Каталог товаров | полный снимок + все страницы | end-of-pagination/cursor, учтённое количество; пустой каталог подтверждён отдельно |
| Продажи | день/период × запрос | доказан конец пагинации и проверены пропуски внутри окна |
| Заказы | день/диапазон × cursor/offset | все страницы пройдены; при ограничении сохранён resume cursor |
| Финансы | день × последовательность ID операции (например rrdid) | pagination exhausted и дневная сверка; cursor и состояние дня сохранены |
| Реклама | кампания × окно дат | отдельный статус каждого campaign-window; empty не спутан со skipped/error |
| Остатки | снимок × страницы/склады | собраны все части снимка; лимит страниц не интерпретируется как нулевой остаток |
| Платное хранение | день отчёта × страницы/детализация | завершён отчёт и сохранён корректный empty-ответ |
| Карточки/конкуренты | объект × момент наблюдения | полнота снимка известна; отсутствие объекта не считается отсутствием изменения |

Если API не даёт доказать полноту, покрытие остаётся unknown/partial. Максимальная дата события и HTTP 200 не доказывают, что интервал полный.

### 4.3 Состояния загрузки, watermark и catch-up

Статусы: SUCCESS, SUCCESS_EMPTY, PARTIAL, RETRY_WAIT, AUTH_BLOCKED, FAILED. Для каждого фиксируются run ID, диапазон, длительность, endpoint/category, запросы/страницы, retries и ожидание rate limit, cursor, число строк по слоям, expected/covered units, reconciliation и безопасный итог.

Watermark — последняя непрерывно закрытая единица источника, а не MAX(event_date) и не время последнего запуска. Загрузка учитывает окно поздних исправлений. При 401/403 источник останавливается до исправления credential; повтор тем же токеном не крутится. При 429 соблюдается retry hint и не создаётся шторм запросов. Сетевой сбой возобновляется только с сохранённой контрольной точки.

Замер восстановления сравнивает начальный checkpoint с текущей границей отдельно по каждому источнику. Отчёт должен показать время, запросы, ожидания, retries, полноту, разрывы, дубли, сверку и результат повторного запуска. «Быстро» не считается успехом без полного покрытия и сверок.

**Текущий статус:** действующего WB-токена сейчас нет. Проверка автоматического catch-up до текущей границы и фактическая скорость API — НЕ ПРОВЕРЕНО/БЛОКИРУЕТСЯ до появления credential. Исторический одиночный замер скорости не заменяет end-to-end тест.

**Текущие дефекты, обнаруженные аудитом:** freshness gate ряда источников опирается на MAX(event_date); bulk продажи не доказывают полноту всех страниц; проход заказов ограничен страницами и не везде устойчиво возобновляется из отдельного запуска; внешний freshness gate может обойти campaign-window очередь рекламы; некоторые WB entry points выставляют WB_SSL_NO_VERIFY=1 по умолчанию. Эти дефекты подлежат устранению до подтверждения надёжного catch-up. TLS verification всегда включён; при проблеме настраивается доверенная CA, а не отключается проверка.

### 4.4 Сохранённые наработки загрузки — не удалять при чистке

В коде уже есть отдельные стратегии, их нужно укреплять и проверять, а не заменять общим новым загрузчиком без сравнения:

- **Финансы:** `scripts/wb_finance_canonical_default_runner_v1.py` выбирает bulk для закрытой истории и live-tail для свежих дней (по умолчанию последние 3 календарных дня). `scripts/wb_finance_canonical_bulk_runner_v1.py` и `scripts/wb_finance_canonical_live_tail_runner_v1.py` имеют разные режимы завершения; `scripts/wb_finance_canonical_closed_period_runner_v1.py` отвечает за закрытые периоды. У live-tail предусмотрено тихое первичное presence-зондирование → проверка, открыт ли источник → ограниченный follow-up → provisional материализация → строгая usable-закрывающая проверка. Rate-limit или отложенный контур никогда не доказывают пустой день.
- **Закрытые финансовые дни:** текущая последовательность использует продолжение с максимального rrdid, если день уже материализован; replay дня для контроля; повторную проверку после полезного прироста; затем saturation close. Saturation допустима лишь при terminal/no-content, отсутствии нового rrdid и роста суммы/диапазона после полезной итерации; duplicate-only хвост сам по себе не добавляет денег. Сохранён и принцип multi-pass close: page cursor действует внутри прохода, строки повторных проходов дедуплицируются по rrdid, сломанный cursor/429/пустой continuation завершает попытку, но не день; повторный проход начинает день с начала. Исторический stable-mode использовал минимум 3 прохода и требовал два последовательных прохода без новых строк/роста; текущий canonical mode дополнительно использует saturation checks. Количество проходов, паузы, endpoint-лимиты и RPS из экспериментов не считать вечными нормативами — сверять с кодом/тестами и перепроверять перед изменением.
- **Реклама:** `scripts/wb_ads_canonical_runner_v1.py` имеет очередь срезов campaign × date window, сохранение состояния и прогресс по completed/pending/retry/error. Сохранять эту декомпозицию и resume; исправить внешний freshness gate, который способен перескочить внутреннюю очередь. `429` должен остановить/охладить соответствующий контур, а не создавать шторм.
- **Общий ingestion:** `src/ingestion/source_registry.py` описывает источник, chunking, grain и loaders; `src/ingestion/runner.py` создаёт run/chunk, пишет аудит и считает coverage/row loss; connector fetch → raw store → normalizer → idempotent upsert → publish gate. Это полезный каркас, а не доказательство того, что каждый endpoint уже полон.
- Raw страницы, resume/cursor, дневные статусы финансов, очереди рекламы, SQL сверки и тесты загрузчиков — часть накопленной работы. Сохранять и улучшать их при следующих итерациях; не заменять локальные scripts и данные массовой очисткой.

Текущие retry delays, page caps, RPS, concurrency и признаки close в раннерах — наблюдаемая конфигурация/история конкретной стратегии. Перед её переносом проверить действующие официальные лимиты API и тесты; не копировать экспериментальное число как правило без новой валидации.

## 5. Модель данных и идентичность

Каждый слой сохраняет grain, ключ, бизнес-время, время получения, marketplace, источник и lineage. Raw неизменяемо хранит полученное (с безопасной редактировкой секретов); staging сохраняет структуру источника; нормализованный слой сохраняет типы и явные ключи; marts содержат расчёты с версией правил; API/UI отображают snapshot и его качество.

Текущие основные grains:
- товар — marketplace + source product identity;
- продажа/возврат — строка события/операции источника;
- заказ/отмена — строка или статусное событие заказа;
- финансы — строка финансового отчёта/операция с ID источника;
- реклама — дата × кампания × доступные товарные/placement dimensions;
- остаток — снимок × товар × склад × тип доступности;
- наблюдения карточки/конкурента — объект × фактическое время наблюдения.

Основные WB staging-контракты: `stg_wb_product` — source identity/raw update time; `stg_wb_sale` — sale_date + исходный тип/знак; `stg_wb_order` — order_date, заказ не равен продаже; `stg_wb_finance` — operation_date + rrdid/type/source amount/sign; `stg_wb_ads` — date + campaign и реально полученные товарные dimensions; `stg_wb_stock` — snapshot_date + product/warehouse/availability; `stg_wb_paid_storage` — report_date + detail; `stg_wb_competitor_snapshot`/`stg_wb_product_card_snapshot` — captured_at, точечный снимок; `fact_wb_competitor_observation` — конкурент × свой товар × query × дата; `fact_wb_product_card_observation` — товар × фактический день наблюдения. Точные constraints сверять с DDL и upsert перед изменением.

Эти grains сверять с реальным DDL и API; название таблицы не является доказательством. Канонический товар соединяется только через однозначную bridge-связь marketplace-specific ID. Похожие артикулы сами по себе не ключ. Для каждого join измерять matched/unmatched/ambiguous, потерю/размножение строк и сумму до/после. Не использовать технический placeholder как товар. Unknown остаётся отдельным состоянием.

Исходные суммы, тип операции и знак сохраняются отдельно от преобразованного экономического влияния. Преобразование имеет явную версию mapping. Денежные записи раскладываются без двойного счёта на direct product, store-level, estimated и unmatched.

### 6.3 Сохранённые выводы прежних сверок и bridge-исследований

Эти результаты — ограниченные аудит-снимки, а не текущая гарантия и не бизнес-правило. Сохранять метод проверки и использовать локальные исходные таблицы/экспорты для регрессии:

- В сверке схемы `client_demo_90d_20260408` за 2026-01-09—2026-04-08 продажи сходились raw→stg→mart после dedupe по `sale_id`; финансовые суммы в основном сходились, с небольшими хвостами округления/атрибуции. Рекламный raw spend был 310,509.49 ₽, staging — 109,202.77 ₽; потеря возникла из-за схлопывания `appType` (несколько app-level строк попали в один ключ). Это найденный исторический дефект. В текущих DDL/upsert `app_type` уже включён в PK/collision key; сохранена реализация, но отдельный регрессионный тест и сверка текущей базы ещё нужны.
- В этой же сверке `storage` (6,333 строк; 48,818.59 ₽) и `penalties` (1,950 строк; 435,361.30 ₽) имели слабую атрибуцию `revenue_share_window`. Эти суммы нельзя считать direct product evidence и использовать для точечного действия без проверки исходной связи.
- Для WB основной source identity товара — `nm_id`; `offer_id` вида `wb_nm_*` может быть внутренним bridge label, а не точным ключом рекламного источника. Рекламу связывать через явный `nm_id → bridge → canonical product`; revenue-share fallback оставлять estimated. Для Ozon native identity — `offer_id`, но finance на уровне posting нельзя механически размножать на все товары posting; использовать line item `product_id/sku` и bridge, а остаток держать на posting/store-level.
- В старом revenue-share/attribution analysis рекламные строки иногда получали высокий coverage после barcode fallback, но покрытие конкретного периода не делает такую fallback-связь универсальной прямой истиной. Exact match и fallback должны иметь разный confidence и отображаться отдельно.
- Историческая семантическая модель разделяла подтверждённый operational result и оценку после COGS. Кандидат формулы был: revenue − ads − commission − logistics − services − penalties/withholdings + positive corrections − negative corrections; оценочную себестоимость вычитать отдельно. Формула остаётся КАНДИДАТОМ, пока не проверены исходные знаки, возвраты, типы продаж WB и границы включённых категорий; старый `net_profit` не использовать без выяснения смысла.

Для этих выводов не копировать старые числа в нынешнюю клиентскую витрину: сохранять саму проверку (raw/stg/attribution/mart row flow, appType cardinality, direct vs estimated bridge) и заново запускать на актуальном snapshot.

## 6. Агрегация и финансовая методика

### 6.1 Соединения, дедупликация и окна

Перед join подтвердить уникальность ключей и ожидаемую cardinality. One-to-many размножение допустимо только если описан его смысл и доказана сохранность итога. До и после соединения считать строки, unmatched, ambiguous и суммы.

Дубликат определяется ID/ключом источника и семантикой корректировки, не совпадением суммы/текста. При отсутствии source ID составной ключ — отдельное техническое решение с тестом коллизий. Не удалять похожие строки эвристикой.

У каждой метрики указать grain, timezone, границы окна, freshness и закрытие периода. Отношения считать как отношение сумм числителя к сумме знаменателя, если не утверждена другая методика. Отсутствующий день не заполнять нулём без подтверждения полноты. Сравнивать сопоставимые закрытые периоды.

### 6.2 Деньги и экономика

**ОБЩИЙ КОНТРОЛЬ:** хранить source amount как пришла, включая знак, валюту, исходный operation code/type, дату и ID. Экономический знак/класс — отдельный слой по явному mapping `marketplace + source type → category + sign rule + attribution scope + mapping version`. Запрещены ABS() до определения семантики, классификация только по свободному тексту, удаление unknown и выдуманное распределение общего расхода на товары.

Прямая атрибуция разрешена только при подтверждённой связи в источнике. Расход без связи остаётся store-level/unallocated. Любое распределение по выручке/продажам — estimate, не факт; формула и база показываются отдельно, а клиентская причинность/действие на estimate не строится до решения владельца.

Для опубликованной денежной метрики владелец должен утвердить формулу, состав статей, возвраты/сторно/корректировки, момент признания, налоги/себестоимость, валюту и округление. Пока этого нет — нельзя называть результат универсальной прибылью или обещать экономию. Допустимая сверка: source total = direct product + store-level + estimated (отдельно) + unmatched, без двойного учёта и с явным допуском округления.

**ОТКРЫТО:** полный кросс-маркетплейсный финансовый глоссарий, знаковая таблица и допустимые thresholds.
**ТЕКУЩИЙ ДЕФЕКТ:** часть SQL применяет ABS и текстовую классификацию; хранение местами распределяется по продажам. Эти реализации не считаются утверждённой методикой.

Не выбрасывать существующие слои ежедневного факта, canonical measures, raw/stg audit, granularity reconciliation, unmatched money, pipeline health и data-quality marts. Сверить их определения с этим разделом и исправлять точечно. Таблицы — накопленная проверяемая работа, но их текущие формулы не автоматически утверждены.

## 7. Анализ, причинность и сигналы

### 7.1 Аналитическая процедура

1. Сформулировать вопрос/решение, объект, grain, метрику и окно.
2. Проверить источник, свежесть, полноту, snapshot и сопоставимость периодов.
3. Показать формулу/единицу и абсолютные значения с размером базы.
4. Разложить изменение на компоненты, которые сходятся с общим итогом.
5. Проверить альтернативы, только если данные по ним полны: неполный день/период, состав товаров, остатки, возвраты, цена, реклама, сезон/день недели.
6. Отдельно маркировать факт, интерпретацию, гипотезу и доказанную причину.
7. Указать неопределённость, ограничения и какие данные изменят вывод.
8. Приложить воспроизводимый расчёт/SQL и lineage.

Корреляция, последовательность событий и правдоподобная история не доказывают причинность. Без эксперимента или сильного квазиэкспериментального дизайна можно сказать «связано с/возможно объясняет», но нельзя приписывать точную сумму причины и действие, зависящее от неё. Сравнивать одинаковые полные окна. Незакрытые дни и финансовые периоды маркировать отдельно. Бизнес-пороги, минимум выборки и сезонная коррекция пока ОТКРЫТЫ — не придумывать.

### 7.3 Полная цепочка доказательного анализа

Для денежного изменения проходить от store/product result → выручка и расходы → проданные единицы и заказы → посещаемость/конверсия/реклама/наличие, только когда эти данные доступны и полны. Для расходов — от суммы и source operation → тип операции → прямой товар/кампания/склад либо store-level/unmatched. Не перескакивать от общего изменения к совету «менять цену/рекламу/карточку». Проверять альтернативы и вклад, сохранять факты и подавленные гипотезы, не считать их причиной без идентификации. Декомпозиция не должна дважды распределять одну сумму.

Текущий код `src/services/recommendation_engine_v2.py` проверяет кандидатов в фиксированном порядке: остаток/риск stockout, восстановление тренда, логистика на единицу, цена, реклама, спрос, удельная экономика, однодневное предупреждение, положительное состояние. Это описание существующей реализации, не утверждённая приоритизация. Входные `ProductContext` и quality flags должны подтверждаться происхождением данных, не самоназначаться builder-ом.

Тестовые случаи должны покрывать изменения на уровне товара и магазина: рост/падение результата и выручки; концентрацию эффекта в нескольких товарах; расход без товара; конфликт месячного и недельного направления; дефицит/старый остаток; реклама без сверки; неполный день/период; дубли; неоднозначный товарный join; неизвестную операцию; разные snapshot; низкий объём; повтор сигнала и подавленные действия. Синтетические значения полезны только как тестовые входы и не подменяют размеченные реальные результаты.

### 7.2 Сигнал

Сигнал — наблюдаемое отклонение, гипотеза — возможное объяснение, рекомендация — отдельное действие. У сигнала есть стабильный code, объект/grain, формула и версия, окно/baseline, значение и единица, snapshot, severity, lifecycle и ограничения. Состояния: candidate → active → monitoring → resolved; дополнительно blocked и suppressed. Blocked означает нехватку/конфликт данных, suppressed — сохранённый, но не основной сигнал; ни один не равен «проблемы нет».

Новый прогон не создаёт новый эпизод ежедневно: устойчивый ключ включает правило, объект и условие reopen. Проверяются threshold boundary, пустые/частичные данные, дубли, повторный запуск, reopen и конкурирующие сигналы. Числовые пороги и приоритеты требуют решения владельца и проверки ложных срабатываний на размеченных случаях.

## 8. Рекомендации и клиентская подача

Рекомендация разрешена, только если прошли quality gates, действующий сигнал и доказательство подходят, причина имеет нужный evidence level, действие контролируемое/обратимое, риски ясны, а результат можно проверить. Иначе — signal-only или blocked.

Перед выпуском каждой карточки ответить на семь вопросов: полные ли сопоставимые периоды подтверждают факт; проверена ли причина первоисточником; можно ли измерить/ограничить её вклад; дано ли одно конкретное действие; указан ли срок; есть ли измеримый критерий успеха; безопасно ли действие и не смешано ли с одновременным изменением других факторов. Если факт или причина не подтверждены — бизнес-действие запрещено.

Каждая рекомендация хранит: code и версию правила; объект; факт/период; source/snapshot; класс причинности; одно проверяемое действие; исполнителя/срок; предпосылки, риск и обратимость; неизвестное; дату контроля и метрику успеха; отмену/эскалацию и фактический исход. Один товар может иметь одно главное действие только по документированному tie-breaker; подавленные варианты сохраняются для аудита.

Не обещать эффект, не считать возможную экономию через произвольный процент восстановления и не предлагать изменить цену, рекламу, карточку или поставку без подтверждённой причины. Результат после действия сам по себе не доказывает причинный эффект.

В интерфейсе различать:
- показатель — измеренное значение с периодом/единицей/freshness;
- сигнал — установленное отклонение;
- гипотеза — возможное объяснение с альтернативами;
- рекомендация — действие с критерием проверки.

Состояния current, stale, partial, unknown, blocked, estimated, unmatched и synthetic видимы; неизвестное/частичное не отображается как ноль или «норма». Причинное «из-за» разрешено только при причинном доказательстве. Синтетические демо явно маркируются, никогда не смешиваются с данными аккаунта и не служат подтверждением порогов.

**ОТКРЫТО:** приоритеты действий, пороги, минимальные объёмы и оценка эффекта. Текущая выдача движка сама по себе не доказывает корректность этих решений. Тестовые сценарии в `research/fictional_store/` и примеры старого каталога искусственные; не использовать их как бизнес-факты или актуальные инструкции.

**ТЕКУЩИЙ ДЕФЕКТ:** builder рекомендаций сам выставляет признаки `consistent_snapshot`/completeness для части контекста; эти флаги должны выводиться из реального completion ledger и общего publish snapshot, а не из утверждения builder-а. До исправления качество рекомендации нельзя считать подтверждённым только по этим полям.

Сохранённые тестовые классы полного анализа: дефицит/распределение по складам; органическая видимость; реклама и бюджет/CTR; цена и конверсия; доставка/рейтинг; категорийный спрос и конкуренты; единицы, отмены, возвраты; ad cost/order, логистика и хранение; тарифы/необычные списания; сочетания причин и разнонаправленные store/product итоги. Отдельно тестировать восстановление, одиночный день, малую выборку, новый товар, неполноту и отсутствие значимого ухудшения — это должны быть состояния без действия, не нейросовет.

## 9. API, эксплуатация и безопасность

API/страницы — по фактическим роутам `src/api/main.py` и `cabinet/app/api/`; перед изменением сверить реальный контракт в коде. Внешние ключи доступны только серверной среде. Все write-операции обязаны проверять аутентификацию/авторизацию, принадлежность store, marketplace, сущность и даты; audit actor берётся из проверенной identity, а не из payload.

**ТЕКУЩИЙ ДЕФЕКТ:** API изменения не подтверждает пользователя, `updated_by` доверяет клиенту. Не публиковать такие операции в сети/production до авторизации. TLS verification включён всегда; токены/PII не печатать и не коммитить. До staging просмотреть каждый путь и staged diff. GitHub считать публичным, пока приватность не проверена.

Ежедневный поток проходит bootstrap → источники → marts → analytics → snapshot/publish. Работающий контейнер не гарантирует свежесть и полноту. Проверять run/source state, покрытие, cursor, reconciliation, возраст каждого набора, число blocked рекомендаций и атомарность client snapshot.

Повтор должен быть идемпотентным. Не запускать параллельную копию runtime; проверять lock/process. При ошибке не затирать последний хороший snapshot. Backup PostgreSQL считается проверенным только после restore rehearsal. Диагностический режим не подменяет production публикацию.

## 10. Quality gate и критерии завершения

Проверки идут по порядку:
1. секреты/TLS/доступы корректны;
2. у каждого required source доказаны completeness, freshness и resume;
3. grain, уникальность, joins, row counts и суммы сверены;
4. методика утверждена и вывод не сильнее evidence;
5. один immutable snapshot объединяет все клиентские показатели/сигналы/рекомендации и atomically published;
6. интерфейс показывает stale/partial/blocked/estimated;
7. rollback/backup/recovery определены.

Статусы результата: PASS — доказательства есть и все критерии пройдены; FAIL — критерий нарушен; UNVERIFIED — доказательства нет; BLOCKED — отсутствует доступ/решение/источник. Только PASS разрешает соответствующую публикацию. Диагностическая сборка не может заменить published output.

По изменению оставлять компактный evidence: задача, scope, входы, пути, версии правил, команды и реальный результат проверок, сверки без секретов/PII, независимая критика, ограничения и документный diff. Агентское согласие не доказательство.

## 11. Агенты и итерационный процесс

Использовать роли выборочно:
- **Координатор/интегратор** — единственный владелец scope, решения конфликтов, общего файла и итогового Git change set.
- **Исполнитель** — одна ограниченная область и allowlist файлов; следует этому документу, не изобретает бизнес-норму.
- **Аналитик данных** — read-only проверяет полноту, grain, join, суммы, lineage и расчёты.
- **Независимый скептик («хейтер»)** — свежий контекст, read-only; получает критерии, первичные данные и diff, но не самооправдание автора. Ищет контрпример, ошибочный знак/знаменатель, пропуски, fanout, смешение, неполный период, ложную причинность и риск. Возвращает PASS/FAIL/UNVERIFIED с конкретным доказательством; не пишет новую рекомендацию и не подтверждает без проверки.
- **Ревьюер безопасности/релиза** — только для затронутой безопасности/публикации.

Последовательность: координатор читает эту базу и проверяет Git → описывает цель, область, allowlist и критерии → независимые read-only исследования могут идти параллельно по непересекающимся областям → закрываются решения OPEN → один исполнитель вносит код + изменение этой базы + проверки → аналитик/хейтер проверяют независимо → исполнитель исправляет → координатор проверяет gates и коммитит точные пути. Не запускать агентов на одну и ту же реализацию/файл. Мультиагентность снижает самоподтверждение только при независимых входах и воспроизводимых доказательствах; она добавляет стоимость и не заменяет проверку.

Модель выбирается по сложности шага: быстрая для ограниченного извлечения и механических преобразований с чётким критерием; сильная для неопределённой методики, причинности, финансового решения и скептической проверки. Навык/skill — только повторяемый технический workflow или инструмент; он не содержит проектную бизнес-логику и не заменяет этот файл.

## 12. Git, чистота и актуальность

`AGENTS.md` и этот `PROJECT.md` — единственные корневые проектные инструкции. Новые постоянные Markdown без необходимости не создавать. Изменять эту базу по тематическим разделам; после изменения правила искать старую формулировку, путь, формулу и удалить конкурирующий текст/ссылку в том же change set. Не создавать v2/final/backup/changelog. История — Git.

Генерируемые отчёты и временные данные направлять в уже исключённые `artifacts/`, `exports/`, `logs/` или `test_artifacts/`, не в корень и не в инструкцию. Секреты, реальные дампы, локальные данные БД и пользовательские изменения не удалять при чистке документов. Перед коммитом: документ соответствует коду/решению; ссылки актуальны; нет дубликата нормы; diff ограничен scope; секретов нет; проверки имеют фактический PASS/FAIL; staging только именованных файлов; commit отправлен в рабочую ветку без переписывания истории.

## 13. Очерёдность незакрытой работы

1. **WB catch-up** — получить credential безопасно, исправить TLS defaults и freshness/pagination/resume; замерить с checkpoint до текущей границы, закрыть полноту и повторы.
2. **Финансовые правила** — по исходным строкам утвердить категории/знаки/глоссарий/атрибуцию; заменить ABS/text heuristics; доказать сверку.
3. **Агрегация и публикация** — проверить keys/cardinality; убрать денежный fanout; ввести общий snapshot ID и fail-closed publish gate; запретить diagnostic mode подменять выдачу.
4. **API security** — аутентификация/авторизация write paths и ownership; audit identity.
5. **Анализ/сигналы/рекомендации** — только после данных/методик; пороги и действия утвердить, провести независимую adversarial проверку и ложноположительные кейсы.
6. **Эксплуатация** — расписание/алерты, backup и проверка восстановления, production immutable image.
7. Закрыть каждый пункт только evidence PASS; обновлять этот же файл при принятии правил.

Пункты 1–6 — очередь, не обещание завершения. До токена live WB run остаётся BLOCKED; текущий pipeline не считать надёжным только по локальному историческому замеру.
