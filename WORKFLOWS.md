## Последовательность работы агентов

1. **Координатор:** прочитать `AGENTS.md` и `PROJECT.md`, выбрать профильные инструкции из реестра, записать цель, охват, разрешённые пути, критерий готовности, нужного исполнителя и независимого проверяющего.
2. **Разведка:** если есть неопределённость, назначить независимые read-only исследования разных областей. Каждый получает одинаковый вопрос, но отдельный ограниченный контекст; совместное редактирование одного файла запрещено.
3. **Решения:** сопоставить доказательства с утверждёнными правилами. Не закрывать статус `ОТКРЫТО` догадкой; запросить решение владельца только там, где без него нельзя продолжать.
4. **Исполнение:** назначить одного владельца реализации. Он меняет только разрешённые пути, связанно обновляет код, профильную инструкцию и проверки.
5. **Независимая проверка:** скептик получает критерии, первичные данные/расчёты и diff без рассказа автора о том, почему результат «должен быть верным». Для безопасности подключить отдельного ревьюера.
6. **Исправление:** исполнитель устраняет найденные контрпримеры либо помечает спорный результат `FAIL`, `UNVERIFIED` или `BLOCKED` с доказательством.
7. **Интеграция:** координатор повторяет профильные quality gates, проверяет ссылки/старые формулировки, секреты/PII, точные staged paths и весь staged diff.
8. **Фиксация:** коммитить только связанные проверенные пути. После авторизации владельцем отправить коммит в рабочую ветку; не переписывать опубликованную историю. После фиксации убедиться, что рабочее дерево чистое и нет временных документов/выгрузок в Git.

## Последовательность обработки данных

Для каждого source-unit использовать цепочку из [INGESTION.md](INGESTION.md): checkpoint и план → запросы с pagination/resume → raw + безопасный audit → нормализация по [DATA_CONTRACTS.md](DATA_CONTRACTS.md) → идемпотентный upsert → проверка completeness и сверок → продвижение watermark → [AGGREGATION.md](AGGREGATION.md) → [ANALYSIS.md](ANALYSIS.md) → signal/recommendation gate из [SIGNALS_RECOMMENDATIONS.md](SIGNALS_RECOMMENDATIONS.md) → один проверенный клиентский snapshot и publish.

Пропуск этапа, неполнота required source, неразрешённый join, неизвестная денежная операция или разные snapshot блокируют только зависящие от них показатели/действия. Диагностические данные не подменяют клиентскую публикацию.

## Quality gates и критерии завершения

Проверки идут по порядку:
1. секреты/TLS/доступы корректны;
2. у каждого required source доказаны completeness, freshness и resume;
3. grain, уникальность, joins, row counts и суммы сверены;
4. методика утверждена и вывод не сильнее evidence;
5. один immutable snapshot объединяет все клиентские показатели/сигналы/рекомендации и atomically published;
6. интерфейс показывает stale/partial/blocked/estimated;
7. rollback/backup/recovery определены.

Статусы результата: PASS — доказательства есть и все критерии пройдены; FAIL — критерий нарушен; UNVERIFIED — доказательства нет; BLOCKED — отсутствует доступ/решение/источник. Только PASS разрешает соответствующую публикацию. Диагностическая сборка не может заменить published output.

По изменению оставлять компактный evidence: задача, scope, входы, пути, версии правил, команды и реальный результат проверок, сверки без секретов/PII, независимая критика, ограничения и документный diff. Агентское согласие не доказательство.

## Очерёдность незакрытой работы

1. **WB catch-up** — получить credential безопасно, исправить TLS defaults и freshness/pagination/resume; замерить с checkpoint до текущей границы, закрыть полноту и повторы.
2. **Финансовые правила** — по исходным строкам утвердить категории/знаки/глоссарий/атрибуцию; заменить ABS/text heuristics; доказать сверку.
3. **Агрегация и публикация** — проверить keys/cardinality; убрать денежный fanout; ввести общий snapshot ID и fail-closed publish gate; запретить diagnostic mode подменять выдачу.
4. **API security** — аутентификация/авторизация write paths и ownership; audit identity.
5. **Анализ/сигналы/рекомендации** — только после данных/методик; пороги и действия утвердить, провести независимую adversarial проверку и ложноположительные кейсы.
6. **Эксплуатация** — расписание/алерты, backup и проверка восстановления, production immutable image.
7. Закрыть каждый пункт только evidence PASS; обновлять этот же файл при принятии правил.

Пункты 1–6 — очередь, не обещание завершения. До токена live WB run остаётся BLOCKED; текущий pipeline не считать надёжным только по локальному историческому замеру.
